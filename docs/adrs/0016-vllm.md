# ADR-0016: vLLM for private inference and embedding endpoints

**Status:** Proposed  
**Date:** 2026-10-05  
**Deciders:** vCloud platform owner and Principal Architect  
**Selection:** vLLM is required by Module 1.  
**Scope:** [SSoT and shared implementation contract](README.md).

## Context

vCloud needs controlled local/cloud GPU inference with an HTTP interface consumed by
the RAG application. vLLM provides an
[OpenAI-compatible serving interface](https://docs.vllm.ai/en/stable/serving/online_serving/).
Embedding support is model/task dependent, using
[pooling models](https://docs.vllm.ai/en/latest/models/pooling_models/embed/).

## Decision

- Run non-root vLLM Deployments/Services in `hpc-compute`, separate from the CPU Knative
  API. Use the NVIDIA runtime, the approved device plugin and explicit whole-GPU requests.
  GPU node labels/taints control placement. No MPS daemon, privileged application pod,
  hostPath model cache or unreviewed RDMA device mount is granted by this ADR.
- Provide two private roles: generation (`/v1/chat/completions`) and a separately
  configured, compatible embedding model (`/v1/embeddings`). Do not assume one generation
  model serves both tasks. Generation and embeddings have independent model revisions,
  resource budgets and scalability; verify the selected release's exact endpoint contract.
- Stage licensed model weights and reviewed tokenizer/config artifacts through a
  controlled artifact path, mounted on CSI PVCs. Pin container digests, model revisions,
  quantization and CUDA/driver compatibility. Remote model-code execution is disabled
  unless separately reviewed and justified. No automatic public model download at startup.
- Keep a warm generation replica when the interactive SLO requires it. Bound model
  context, batch/concurrency, queue size and GPU/KV-cache memory. Scale using measured
  queue/token workload and available GPU quota; CPU utilization is not a sufficient
  inference capacity signal. GPU allocation or cold start is not part of every user request.
- The LangChain service calls private TLS-protected endpoints with workload credentials.
  vLLM has no PostgreSQL credentials and no data-store egress. GPU workers for HPC jobs
  use a separately bounded admission queue so they cannot consume all serving capacity.

## Options considered

| Option | Benefits | Costs and limits |
| --- | --- | --- |
| Warm vLLM Deployments | Predictable model lifecycle and private inference | GPU cost, model sizing and capacity management |
| vLLM directly under scale-to-zero | Idle GPU savings in some deployments | Model load/GPU acquisition can exceed interactive latency budgets |
| Hosted inference API | Less local GPU operation | Different data-residency, cost and provider dependency contract |

## Trade-off analysis

Warm inference separates model lifecycle from HTTP autoscaling. Treat multi-GPU or
multi-node parallelism as a tested capacity profile, not an assumed benefit of an
installed MPI/UCX library.

## Consequences

Missing GPUs, incompatible drivers or unavailable weights fail readiness; they do not
trigger an unapproved runtime or public-model fallback. Host HugePages do not allocate
GPU VRAM and do not establish a measured vLLM performance gain.

## Action items and acceptance

- [ ] Pin generation/embedding models and benchmark hardware, driver and runtime compatibility.
- [ ] Prove non-root GPU access, CSI model mounts, tenant request limits and denied DB egress.
- [ ] Measure time-to-first-token, token latency, queue pressure, OOM behavior and restart time.
- [ ] Test streaming cancellation, bounded scale-out and preservation of serving GPU quota.
