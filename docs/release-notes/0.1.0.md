# Twinfra v0.1.0 release notes

**Status: draft for the first dev release; no tag, rc branch or release is
created by WO-40b.** VERSION remains 0.1.0. Stable in the 0.x stream means
accepted for dev use; it does not imply a production or HA profile.

## Included

- Ubuntu 24.04 single-node kubeadm bootstrap, system containerd, Cilium native
  eBPF networking, reviewed host/network guards and local PostgreSQL storage.
- Argo CD GitOps, CloudNativePG/PostgreSQL with the pgvector image, Keycloak,
  APISIX and the console with signed-token validation and role denial.
- Authenticated Valkey for Argo CD; the owner-approved cache restart and
  reconnection were verified. This does not assert upstream Valkey support.
- OpenBao transport/deployment only: initialization, unseal and leases are
  outside the accepted scope.
- MiniStack as the sole emulator after LocalStack removal. Console read paths:
  S3 ListBuckets/ListObjectsV2, EC2 DescribeInstances, DynamoDB ListTables/DescribeTable.
  Persistence is disabled; an emulated EC2 response creates no VM.
- Pinned image locks, licence policy, vulnerability exception/calendar,
  offline/historical CI gates, staging checks and owner-run acceptance.
- WO-31 Amendment 15 display-driver remediation with post-reboot verification.

The [capability statement](../capabilities.md) identifies Dev-verified scope
using the signed WO-04, WO-06, WO-25, WO-31, WO-34 P2 and WO-36/36a receipts.
An implemented component is not automatically an accepted product capability.

## What is not claimed

- AWS service parity, real AWS compute/storage backends or durable emulator data.
- HA, multi-node operation, production readiness, compliance or multi-tenancy.
- Accepted backup/PITR/DR, dynamic secrets, certificate automation or durable
  metrics/logs/traces retention and delivered alerts.
- A 24-hour production soak, completed 48-hour rc window, Foundation 1.0,
  signed provenance verified at deploy or operational GPU/AI/HPC modules.
- Arbitrary Kubernetes/Cilium patch combinations or an automated cross-minor
  platform/data upgrade. Historical retired-lab evidence is not current proof.

## Install the dev profile

1. Select an owner-reviewed immutable revision. Until the release is actually
   cut, there is no v0.1.0 tag or downloadable stable artifact to install.
2. Follow the [cairo-1 prerequisites and numbered owner runbook](../dev-environment.md#part-1-cairo-1-on-bare-metal):
   Ubuntu 24.04 x86-64, at least 24 GiB RAM, VT-x/KVM, Secure Boot/lockdown,
   synchronized time, the reviewed static network, root/containerd capacity,
   a separate 20 GiB PG LV and 20 GiB free VG reserve. The cold cairo-2 seed
   is not a running second region or an accepted HA profile.
3. From that revision, render/check the profile and review the host plan:

   ```text
   python tools/platform_dev.py render
   python tools/platform_dev.py check
   python tools/platform_dev.py host-bootstrap --context twinfra-dev-cairo-1 --check
   ```

4. Only the owner applies the reviewed account/network/storage/bootstrap
   steps, reproduces and stages the locked console/PostgreSQL/application
   images, prepares dev PKI and configures GitOps using that runbook.
   Use verified SSH and CA/hostname-checked HTTPS. No public ingress or
   router port forwarding is part of the accepted profile.
5. Run the [owner acceptance procedure](../runbooks/release-acceptance.md)
   at the selected expected revision with private inputs outside Git.
   Obtain separate tester sign-off; installation alone is not acceptance.

## Update within the 0.1 stream

Review the source/configuration/image-lock diff before every update. Keep the
host and component scope separate; do not rerun a full bootstrap or reset an
existing cluster just to apply release documentation.

For an approved runtime change, reproduce/stage changed locked images, run
staging-check, review the GitOps diff, and follow the component's maintenance
and rollback procedure. The
[etcd/CoreDNS runbook](../maintenance/etcd-coredns-2026-10.md) is an example
of the required preflight, verified snapshot, image-only preview, one-component
apply and verification boundary; it is not a command to repeat that maintenance.
Restore requires its own owner authorization. Argo CD promotion likewise
requires its reviewed pin change and owner apply; these notes do not do it.

After a release exists, fixes land on main first and are cherry-picked with
`-x` to release/0.1 under [RELEASING.md](../../RELEASING.md), then receive a new
candidate and owner acceptance. Tags are immutable. After the accepted Stable
cut the next-version bump is a separate PR; VERSION is not bumped here.

## Path to 0.2.0

0.2.0 is a future release, not a proven in-place migration or a promised date.
Carry forward the accepted 0.1 evidence and close the remaining
[Foundation 1.0 gates](../adr/0052-evidence-first-foundation-1-0.md):
data restore/PITR, staging safety, owner unseal and secrets/certificates,
identity audit/roles/CSRF, durable observability, admission enforcement,
availability/load evidence and provenance verification at deployment.
Foundation 1.0 is a capability gate, not the VERSION value.

Before any 0.2.0 update, publish a reviewed compatibility/migration plan covering
schema/configuration/image changes, tested backup/restore, explicit rollback
or restore requirements and new live tester receipts. Do not assume binary or
stateful-data downgrades are safe. Real S3/EC2 and AWS parity remain gated on
WO-22 and ADR-0033 after Foundation 1.0, rather than being implied by 0.2.0.
